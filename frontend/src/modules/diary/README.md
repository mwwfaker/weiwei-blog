# `modules/diary/` — 日记相关复用件

| 文件 | 用途 |
| --- | --- |
| `DiaryCard.vue` | 日记卡片。`showActions` 打开下面的操作行，`showVisibility` 在元信息里显示「◉ 公开 / ◌ 仅自己」。 |
| `DiaryTree.vue` | **时间树**：一条从下往上的时间轴，日记当挂件挂在轴上。左右按 id 哈希分配（稳定 + 打散，且不会连续三篇同侧），年份挂小牌子；**枝叶的浓密跟着写作量走**（前后 21 天的篇数 → `--lush`，四片叶子错开阈值出现）；**右侧一条可点击的时间表**（一格一篇、居中聚焦、渐隐）。入场是**交叉**的（左边那张从树干另一侧扫过来，右边的反过来），增删日记时用高度折叠让树连续长高 / 变矮。卡片仍是 `DiaryCard`，行为与列表页一致。 |
| `DiaryEditorDialog.vue` | 写 / 改日记。可见范围默认值来自 `stores/profile.js`。 |
| `DiaryReaderDialog.vue` | 阅读弹窗。编辑按钮只在本人（或本机草稿）时出现。版面走 `modules/modal/ReadingSheet.vue`：日期/标题/标签与底部按钮固定，**只有正文滚动**。正文按行切成段落排（首行缩进两字 + 两端对齐 + 段间距），落款单独右对齐收尾——判定见文件里的 `SIGN_LINE`，**有几篇没有落款，不能认定最后一行一定是它**。 |
| `DiaryImportDialog.vue` | 导入确认：先把文件解析成草稿让人核对，确认后才写库。一个文件里装很多篇会按日期拆开；顶端有「统一发布权限」，一次给所有草稿定公开/私密。写入期间按钮禁用并显示进度（见下）。 |

## 为什么是「时间树」

日记天然属于时间。列表把时间压成一列日期文字，树把它变成一条**能看见的轴**：
越往上越新、越往下越早，一眼看得到自己写了多久。几个决定值得记下来：

- **左右不是每帧随机的。** 真用 `Math.random()`，任何一次重渲染（搜索、切标签、
  改可见范围）所有挂件都会左右横跳。所以按 id 做 FNV-1a 哈希：同一个 id 永远同一侧，
  看起来乱但稳定。哈希还要**避免连续三篇同侧**，否则一边堆成一坨、另一边空着。
  （第一版用「累加取奇偶」，对连续的 id 退化成 `LRLRLRLR` 的拉链——规律得不像随机。）
- **入场方向由所在侧决定，而且距离要用百分比**：左边那张从右往左、右边的从左往右，
  用的是**卡片自身宽度的 52%**（≈220px），所以左边那张会从树干**另一侧**扫过来——
  两张对着走，才叫「交叉」。最早两版用固定 46px / 64px，用户两次反馈「看不到左右有别」：
  卡片有 430px 宽，几十像素的位移在余光里根本不算方向。
- **过渡写在挂件自己身上，不靠别处的 `.reveal`**：`.reveal` 的 `transition` 声明在前面的
  样式表里，任何一次追加都可能把它顶掉，那时入场会直接跳到终点（等于没有动画）。
  同样理由，这里**故意不写 `.tree-move{transition:transform}`**——它会把挂件自己的
  `transition` 整条顶掉，正在入场的挂件一旦同时拿到 move 类，就会「啪」地跳过去。
  手机是单侧布局（树干靠左），那一边统一从树干往右展开。
- **增删日记时让树真的长高 / 变矮**：折叠的是节点自身的高度（`max-height → 0`），
  不是靠 FLIP 位移补间。删除时 Vue 会先把要走的节点留在 DOM 里播 leave，播完才移除——
  那时其余节点的位置才变，而那一刻已经没有新的更新了，FLIP 补不上，
  树干会在移除瞬间「啪」地缩一截。高度折叠是连续的，树干（`bottom:0`）跟着连续变短。
- **卡片仍然复用 `DiaryCard`**：操作行、可见范围、点击阅读的行为与列表页完全一致，
  树只是换了一种摆放方式。只把它的玻璃模糊关掉——51 个 `backdrop-filter` 一起滚动太贵。

## 右边那条时间表

一条**居中聚焦**的窄带：当前读到的那一年摆正中间，上下的年份按固定步长排开，
越靠边越淡（渐隐交给 CSS 的 `mask-image`，不是逐条算透明度——逐条算的话
透明度变化和位置变化对不齐，看着会「跳」）。**居中那条要浅**：重色会把视线从正文上拽走，
它只是个路标，所以不加粗、不用深色。

- **可以点**：点一格就平滑滚到那一篇。
- **一格一篇**，不是一格一年——这样才能细化到每篇日记的时间；当前那一格显示完整日期
  （`2023.06.10`），跨年那一格常显年份。刻度位置**按「篇」等距**，不按树里的像素坐标：
  树可以上万像素高，直接映射到 420px 的带子上会挤成一条缝，一篇都分不出来。
  像素位置（`tops`）只用来算「当前读到哪一篇」和点击跳转。
- ⚠️ **那条 sticky 元素是 `height:0`，子元素必须绝对定位。** 一开始给子元素用了
  `margin-top:-210px` 想把它居中，结果那 -210px **穿透上去**把整棵树往上拽了 210px
  （外边距塌陷：父元素没有 border/padding、高度又不是 auto），现象是「树突破了上限穿上去」。
  绝对定位的子元素不参与外边距塌陷。
- 它靠着 `margin-right` 的负值推进树干右侧的留白里，比贴在内容边上更靠右。
- `activeIndex` **是小数**（落在两篇之间就取中间值），否则每翻一篇跳一格会很生硬。
- 判断「当前读到哪一年」的那条线取视口 **42%** 而不是正中：视线停在屏幕中上部，
  用正中会永远慢半拍。
- 只在 `min-width:1000px` 显示。刻度是从 `entries` 推导的（computed），所以**没有 JS 时也在**，
  只是位置停在第一格——这比早先「无 JS 就整条不渲染」更好，不会先空一块再冒出来。
- 滚动监听是 `requestAnimationFrame` 节流的，并且 `passive: true`。

## 点开阅读弹窗时，弹窗从哪一边进来

`DiaryTree` 在 `open` 事件里带上挂件所在的一侧（`$emit('open', entry, node.side)`），
`DiaryPage` 交给 `diaries.openReader(entry, side)`，store 把它存进 `selectedDiaryFrom`，
`DiaryReaderDialog` 再传给 `ReadingSheet` 的 `from`。于是**点左边的挂件弹窗从左进、
点右边的从右进**，视线不用跨过整屏去找它。

首页日记碎片与归档页没有「侧」的概念，它们也调 `openReader`（不传第二参）→ 默认从右。

## 枝叶的浓密是数据给的

「写得多的时间段枝繁叶茂」不是装饰，是这棵树想表达的第二层信息：每篇按
**前后 21 天内有多少篇**算一个 0~1 的茂盛度，挂在卡片对面的那半边。

真实数据（51 篇）跑出来的分层：2023 年 5–6 月那一段窗口内 13~16 篇 → `lush` 0.81~0.91；
2025-02-07 与 2026-02-09 全年只此一篇 → 0.2（下限）。所以疏密一眼看得出来。

三个实现上的点：

- 茂盛度是 `0.2 + 0.8 × 归一化^0.65`。**下限 0.2 是有意的**：完全光秃的树干看着像没长起来；
  指数 0.65 是把中间段拉开，否则少数几篇全挤在 0.9 一档。
- 四片叶子用 `clamp(0, (lush - 门槛) × 斜率, 上限)` **错开出现阈值**——纯 CSS 就能做条件显隐，
  不用为每片叶子写一个组件分支。
- 枝叶挂在卡片**对面**那半边（卡片在左就挂右），所以一行里两侧都有东西，树干不会显得空。

## 右边那条时间表为什么是量出来的

刻度**不是按时间均分**，而是每到一个新年份，取那一年第一篇挂在轴上的**实际像素位置**
（`offsetTop`）。卡片高度不一，按时间均分的话刻度和日记就对不上，那这条表也就没用了。
窗口宽度变化会引起正文回流、卡片高度变化，所以挂了 `ResizeObserver` 重新量。

它只在 `min-width:1000px` 显示，并且**没有 JS 时整条不渲染**（`ticks` 为空）——
否则会留下一排飘在空中的年份。桌面要让出这条表的宽度，而且**左右都要让**：
只让一边，轴就不在内容中间了。

## 两个视图共用一张卡片

日记页有「我的日记」和「公开日记」两份列表，结构一致、只差一个操作行和一行元信息。
差异做成了两个布尔 prop，而不是两个组件——否则以后改一处排版要改两遍。

## 日期格式

日记的日期是 `2026-09-30`。卡片上显示成「30 / 2026 / 09」，归档页把它归一化成 `2026.09`
（文章的日期本来就是 `2026.09.18` 形态）。归一化在页面里做，卡片只管显示。

## 导入不丢内容

关闭确认弹窗不会丢掉已解析的草稿——它留在 `stores/diaries.js` 的 `importReview` 里，
重新打开还在。服务器拒绝的那几篇也会留在同一条列表里，方便重试而不是重读文件。

## 「整合日记」怎么拆成一篇篇

拆分规则在 `services/diaryImport.js`（纯函数，`verify:diary` 直接 import 它对拍），
**不在弹窗里**——规则错了只会表现成「多了几篇很长的、少了几篇」，而这直接写进数据库。

- 认的日期头：`2023 年 5 月 29 日 周一`、`2026年9月21日`、`2024-05-05`、`2024年11月28日。`
  （整行锚定，所以正文里提到日期不会被切开）。星期几不进标题，标题统一成 `2023年5月29日`。
- **也认「正文里自带日期」的篇**：`今天是2025年2月7号，也是农历正月初十。……` 这种没有独立
  日期行的日记，以前会被并进上一篇（真实文件里就漏过一篇：50 篇只拆出 49 个独立篇）。
  这一行本身留在正文里。一个文件一篇时它不会切成「空篇 + 真篇」，见 `matchInlineDiaryStart`。
- **结尾那行「时间 莫唯唯」原样留在正文里**，没有单独解析成字段：少一处格式假设，
  导出与阅读就还是当初写下的样子。
- 一行都不丢是硬要求：核对方式是「源文件非空行数 − 日期头行数 = 各篇正文行数之和」。
- 顶部不属于任何一篇的段落（例如文件总标题）会单独留一篇（`date` 为空，由 store 补今天），
  **宁多一篇让人删，也不悄悄吞掉**。

## 为什么「确认并保存」要防重复点击

一次点击会**并发发几十个请求**（实测 50 篇约 1 秒）。按钮在那期间不禁用的话，
手快的人点两下就是两份完全相同的内容——而且它们标题日期一模一样，事后只能配对删。

所以 `confirmImport` 里有两道：`importing` 为真时直接返回（不只是把按钮变灰），
以及按钮显示 `保存中 12 / 50` 让人知道它在跑。`importing` 在 `finally` 里复位——
不放 finally 的话，一次网络异常就会让按钮永久卡在「保存中」。
