# 唯唯园

面向个人创作的响应式博客项目：暗色星空视觉、音频律动粒子、滚动揭示与极光背景动效、文章/分类/标签、日记、相册、音乐、留言、友链、时间归档、个人介绍与管理入口，以及一个**金融学自学路线「学习」板块**。

## 项目结构

没有后端进程：前端是静态站，账号 / 数据库 / 对象存储全在 Supabase。

```
frontend/            Vue 3.5 + Vite，唯一会被构建和部署的东西
  src/app/           骨架：路由表、页面注册表、导航表、页面调度、全局提示、登录守卫
  src/layouts/       应用外壳：侧边栏、顶栏、常驻播放器与弹窗的挂载点
  src/pages/         15 个页面，一个页面一个文件夹（各自带 components/ 与 README.md）
  src/modules/       跨页面复用的块：页面通用件、弹窗外壳、文章/日记/相册/音乐/资料/粒子
  src/stores/        全部跨组件状态（Pinia）
  src/services/      与外部打交道：HTTP、对象存储、歌词接口、OCR、纯计算
  src/composables/   可复用的组合式函数（目前是动效层）
  src/data/          接口还没答上来时用的内置示例
  src/styles/        样式，按层叠顺序拆成若干文件
  scripts/           自检脚本（不引依赖，只用 Node 内置模块）

supabase/            数据层的权威定义：schema.sql、apply.mjs、歌词中转 Edge Function
```

## 权限模型：看是公开的，改要登录

全站只有一条规则：

| 动作 | 是否需要登录 | 范围 |
| --- | --- | --- |
| 浏览文章 / 日记 / 相册 / 音乐 / 公开日记 / 绩效数据 | 不需要 | 所有人看到的**完全一样**——所有账号里标记为「公开」的内容 |
| 新增 / 修改 / 删除 | 需要 | 只能动自己账号里的数据；别人的记录一律按不存在处理（404） |

登录不会让你多看到或少看到公开内容：它只是在自己那份公开内容之上，再叠一层自己账号里的**私密**内容（`visibility: PRIVATE`）。所以不存在「登录后反而看不到别人的公开文章」这种落差。

服务端把这条规则落在两类接口上：

- **`GET /api/public/**`：匿名可读**，返回所有账号的公开数据，管理员与访客拿到的是同一份。
  - `/api/public/articles`、`/api/public/diaries`、`/api/public/media`、`/api/public/media/music`
  - `/api/public/perf/workspaces`：绩效工作区，按账号分组返回 `ownerId` / `ownerName` / `queues` / `members` / `entries`
- **其余 `/api/**`：需要登录**，并且一律按 token 里的账号过滤（`owned()` 校验，别人的 id 返回 404）而不是 403——不暴露「这条记录存在」这一信息。

**未登录只能看，不产生任何可写数据。** 点「写文章 / 写日记 / 上传照片 / 上传音乐 / 导入日记 / 编辑资料」会直接把你带到登录页，而不是在本机起草一份之后又想方设法合并进某个账号。绩效计算器对访客是只读的（顶栏会显示「公开只读」）；登录后打开自己那一份才可以编辑，查看别人的那一份始终只读——否则切换查看别人数据时的防抖保存会把别人的名单写进自己的账号。

> **绩效数据从「只在本机浏览器」改成了「服务器上公开可读」。** 如果里面是同事的工时和工资，请先确认公开这件事没问题，再往公网环境发布。

## 绩效计算器

**这是一个独立工具，不是博客的一个页面。** 从顶部导航「更多 → 绩效计算器」进入，或从创作管理页的「绩效计算器 →」进入；进去以后博客的侧边导航、顶部栏、粒子背景和播放器都会收起来，它自己占满整屏，自己的顶栏上有「← 返回博客」。

### 怎么用（按实际工作流程设计）

1. **员工名单**：点「批量粘贴邮箱」一次把小组的人贴进来（每行一个邮箱），**姓名 = 邮箱里最后一个 `.工号` 之前的部分**（`zhangwei.5406@…` → `zhangwei`），也可以改成中文名。这里每人填**一次**就够的固定项：月要求工时、抽调时长、加班时长、三薪时长。
2. **录数据**，两种视图随便切：
   - **按员工**（默认）：一行一个员工 → `员工 | 队列 | 实际 AHT | 审核量 | 标准时长 | 审核工资 | 本月合计`。先选他在哪个队列，再填两个数字。要填的两列有底色标出来。
   - **按队列**：选一个队列，一次列出全组人，适合配合「截一个队列的图」批量填。
3. **导入截图**：选好队列，上传该队列的截图（或从飞书复制文本粘贴），识别结果先进入核对表，确认后写入该队列每个人的 AHT 与审核量。

一个人做多个队列也没问题：数据按「员工 × 队列」存，每个队列按各自的单价计价，再把个人的本月合计汇总起来。

### 关于截图识别（实测结论，不是猜测）

拿你那张真实截图跑完 OCR 之后得到的结论：

| 字段 | 识别正确率 |
| --- | --- |
| 审核量（7167、5784…） | **12/12** |
| 工号（5406、5402…） | **12/12** |
| 邮箱文字 | 约 0/12 |

`examp` 会被稳定识别成 `exampfech`，截图上的打码横杠还会往名字里插字符（`zhangwei` → `zhangififwei`）。**所以匹配不靠邮箱文字，而是靠邮箱里的工号**——工号 OCR 完美，且每人唯一。

另外 OCR 有时会吞掉小数点（33.42 被读成 3342），解析器按位数补回来并标记为「推断的」，请核对。

两个队列级兜底：
- 邮箱里被插入中文或空格的整行（`examp 有 ech.com.cn`）也能救回来——解析是逐行做的，只要行里有 `@` 就能取到工号。
- 名单为空时导入会按工号自动建人。

**从飞书直接复制文本粘贴**仍然是最准的方式（精确解析，没有识别误差）。

### 公式

| 指标 | 公式 |
| --- | --- |
| 标准 AHT | `ROUND(24480 ÷ KPI, 2)` ← **KPI 是输入，AHT 是算出来的** |
| 单价 | `(1800 × 标准AHT) ÷ (月要求工时 × 3600 × 0.85)` |
| 审核工资 | `审核量 × 单价` |
| 标准总时长 / 实际总时长 | `标准AHT × 审核量` / `实际AHT × 审核量` |
| 月实际工时 | `实际总时长 ÷ 3600` ← **算出来的，不用填** |
| 月度审核效率 | `标准总时长 ÷ 实际总时长`（小组汇总用加权的 Σ标准 ÷ Σ实际） |
| 完成度 | `审核量 ÷ (KPI × 月要求工时)` ← **口径待确认** |
| 补时工资 | `审核工资 × 抽调时长 × 0.85 ÷ 月实际工时` |
| 加班工资 / 三薪工资 | `加班时长 × 31` / `三薪时长 × 62` |
| 合计 | `审核工资 + 补时工资 + 加班工资 + 三薪工资` |

测试：`npm run verify:perf`（112 项，含 17 个队列由 KPI 推出的 AHT 与表格逐个核对、多队列汇总，以及「数据重置」的 30 条边界断言）、`npm run verify:ocr`（41 项，含**用你真实截图的真实 OCR 输出**做的回归：12 人全部匹配、12 个数全部正确）。

单价用的是**四舍五入到两位小数之后**的 AHT。这一点是验证出来的：用 17 个队列反解月要求工时都收敛到 184 小时，用未取整的 AHT 就会散开。

**数据存放**：登录后存在服务器（`perf_queues` / `perf_members` / `perf_entries`，按账号隔离），换设备也能用；未登录时只存本机浏览器（键名前缀 `weiwei-blog-perf-`）。**读取是公开的**——任何人不登录都能通过 `/api/public/perf/workspaces` 看到全部账号的绩效工作区，写入仍然只认登录账号。详见上面的「权限模型」。

### 关于 OCR 的说明

截图识别对「小字 + 邮箱 + 数字」这类表格不可能做到 100% 准确，邮箱里字母数字混排时尤其容易出错。所以设计上**强制经过人工校对一步**，并优先推荐「从飞书复制文本」——那条路径是精确解析，没有识别误差。

## 视觉与动效

- **极光背景**：`body::before` 上的一层缓慢漂移的径向渐变，只动 `transform`，不重绘渐变。
- **粒子背景**：画布在 `z-index:0`，页面内容在其上且背景透明。颜色按当前主题逐帧给出（深色用亮薰衣草、浅色用深蓝紫），**不使用 `mix-blend-mode`**——旧写法用 `screen`，浅色主题下会把粒子合成到接近全白而完全看不见。
- **粒子随音乐律动**：播放音乐时用真实频谱驱动半径、亮度、连线距离与连线粗细，并做了「快起慢落」的包络，看起来像节拍而不是闪烁的读数。
- **滚动揭示**：`v-reveal` 指令用 IntersectionObserver 逐块淡入上浮；隐藏态由 JS 添加，所以脚本未执行时内容照常可见。用 `translate`/`scale` 独立属性而非 `transform`，因此不会与卡片的悬停位移互相覆盖。
- **下滑收起导航**：向下滚动时左侧品牌向左滑出、右侧资料区向右滑出、导航栏变矮，中间导航保留；向上滚或回到顶部时恢复。滚动处理带 **rAF 节流 + 26px 迟滞 + 320ms 冷却**，方向刚变不会立刻反弹；收起位移只走 74% 并配长缓动，所以是「让开」而不是「被甩出去」。
- **右下角音乐盒：收起是一颗小唱片，悬停向左展开**。平时只占一个 58px 的圆，播放时唱片旋转 + 呼吸放大 + 电平柱跳动，「在不在播」一眼可见且不挡视线；鼠标滑上去（或键盘聚焦）才向左长成完整卡片——曲名、进度、上一首/下一首、进音乐页。
  - 旧写法是一张常驻的卡片，悬停从 300×52 撑到 430×200，**而且过渡的同一个元素上带着 `backdrop-filter`**：等于每帧重新模糊一遍背景，尺寸一变就掉帧。现在过渡的只有宽高、圆角和两层内容的透明度，背景是实色。
  - 两层各自固定尺寸、都贴着容器右下角，所以「容器变宽」被读成「卡片向右固定、向左长出来」，展开过程中卡片里的文字不会跟着宽度反复回流。
- **音乐页：左播放器 / 右歌词**，和主流播放器一样的分工。
  - **两栏严格等高**。以前歌词栏自己写了 `max-height:560px`，而播放器栏的自然高度超过它，于是左右两个板块的底边差了一截。现在歌词栏不再自己限高，由 grid 的 `align-items:stretch` 拉到一样高。
  - 歌词**居中**排布，唱到的那一句放大、变高、加背景与光晕。放大用的是 `transform:scale()` 而不是改 `font-size`——改字号会让整个列表回流，每次换行都可能抖一下；transform 只影响合成层，观感完全一样。
  - 点某一句直接跳到那一句（整行可点，回车也行）；**你手动滚动后自动跟随会暂停 4 秒**，免得想回头看上一句时被拽回去。
  - 解析歌词期间右栏显示骨架行 + 流动微光，而不是一句提示悬在中央。
- **音乐板块（四种可视化可切换）**：
  - **频谱**——以中线对称的圆角柱状，渐变 + 光晕；待机时是一条缓慢起伏、高度明显不同的曲线，不会塌成一条虚线；
  - **矩阵**——长条矩阵：频谱铺成 4 行 × 若干列，每格一根从格底往上长的长条，条顶压一个缓慢下落的峰值帽；相邻两行在频率轴上错开半格，越靠上的行越暗越收敛，于是四行叠起来有纵深而不是同一张图复制四遍；
  - **声波**——连续平滑的波形曲线，渐变描边 + 柔和填充面积；
  - **涟漪**——黑胶唱片持续旋转，声浪一圈圈向外扩散，中心随节拍鼓动。
  唱片周围的涟漪一直存在；模式选择记在本机。
- **卡片与按钮**：悬停抬升、描边发光、图片缓慢放大、主按钮光泽扫过。所有缓动统一到较长的 `cubic-bezier(.22,.9,.24,1)`，位移量整体调小。
- **文字**：标题渐变光泽流动，小节标题前的小横线来回扫光。
- **页面与弹层**：切换带位移过渡（不再用模糊，模糊在多数元素上又贵又显生硬），弹窗回弹入场，提示条滑入。
- **明暗主题**：所有背景都走主题变量。曾经有几处硬编码颜色在切换后很突兀——文章封面占位在浅色下是深蓝紫块、个人介绍卡片在深色下是一整块白——现已修掉，并有一个自动审计脚本按「背景亮度与页面相反」把这类问题扫出来。
- **无障碍**：全部动效都在 `prefers-reduced-motion: reduce` 下自动关闭。

### 关于粒子为何能/不能跟着音乐

| 音源 | 是否驱动粒子 | 原因 |
| --- | --- | --- |
| 本机选择的音频文件 | 是 | `blob:` 同源，Web Audio 可读取 |
| 上传到对象存储的音乐 | 是 | 音频元素带 `crossorigin="anonymous"`，MinIO 的 CORS 允许读取 |
| 外部 HTTPS 直链（MUSIC_URL） | 否，退化为缓慢呼吸 | 不加 `crossorigin` 才能保证外链能播；而浏览器不允许 Web Audio 读取跨域流 |

`analyser` 的 Web Audio 图只建一次并复用：同一个 `<audio>` 元素重复调用 `createMediaElementSource` 会抛 `InvalidStateError`，那会让「播过在线音乐后再播本地音乐」永久失声。

### 图是怎么画出来的（为什么以前会卡）

全站常驻画布和曲库列表加起来，是手感的全部来源，所以都做了收敛：

- **频谱数据本身**：`fftSize` 原来是 **128**，也就是只有 64 个频点，而柱子上限有 44 根——平均每根柱子摊到一个频点，每根柱子都在跟着单个频点的抖动乱跳，这就是「三种特效波动太大、起不到效果」的直接原因。现在 `fftSize` 提到 1024（512 个频点），每根柱子摊到十几个频点**取平均**，并把 `smoothingTimeConstant` 提到 0.86、回落改成缓释，读数才是稳的。
- **曲目行的逐行模糊**：曲库每一行都被一条历史分组规则加了 `backdrop-filter: blur(14px)`，而它正后方就是一直在动的粒子画布——等于每帧对每一行重新模糊一遍背景。这是最贵的一处，已经把这行从那条分组规则里摘出去，改用实色背景。
- **粒子背景**：连线原来是 O(n²)——132 个粒子两两算距离，每帧 8600 多次 `Math.hypot`，而且每条命中的连线都单独 `beginPath + stroke` 一次。现在改成格子分桶只比相邻格子，并把同一档透明度的连线合并成一条路径一次描边；`devicePixelRatio` 封顶 1（铺满全屏的画布按 1.25 倍渲染等于多涂五成像素，而粒子只有一个像素大）。标签页切到后台时停笔。
- **频谱画布**：以前不管在不在播放都跑满 60fps，而音乐页上同时挂着三块画布。现在分档：真实频谱取 `maxFps`（默认 45，唱片涟漪只要 30）、外链播放 30fps、纯待机 15fps，滚出视口或标签页在后台时一帧都不画；频谱柱的渐变按高度量化成 24 档缓存复用，不再每根柱子每帧 `createLinearGradient`；`devicePixelRatio` 封顶 1.5。
- **起播那一瞬不和播放抢资源**：老曲目要现去解析歌词时，`probeDuration` 会另建一个 `<audio>` 把同一个文件再解码一遍，正好和用户的播放抢 CPU。现在正在播放的那一首不探时长（用播放器读到的值，还没有就先不带时长去搜），而且现去解析会推迟 1.2 秒，让音频先起来。
- **样式冲突**：样式表是追加式演进的，同一个选择器会在不同层次里被反复定义。之前 `.music-row` 有 6 条互相打架的全局规则、`:hover` 有 4 条不同的位移（最后一层还带 `!important`），暗色主题 16px 圆角、浅色主题 10px。现在曲目行只剩一条基准规则 + 一条窄屏覆盖 + 一条主题配色。样式拆成了 `frontend/src/styles/` 下的若干文件，**import 顺序就是层叠顺序**，不要调整。

## 音乐与歌词

歌词的解析发生在**上传的时候**，不是打开页面的时候：上传时手里有完整文件（能读内嵌标签），上传的人又是登录状态（能把结果直接写回数据库）。于是访客打开音乐页时，歌词已经是一行现成的文本——不用等，也不会因为在线接口挂了就看不到。

上传是一条**后台流水线**：上传到对象存储 → 写入音乐库 → 解析歌词 → 完成。它显示为音乐页里的一条**内联导入队列**（曲库上方），一条一个文件，可以一次导入好几首。

这里刻意**不用弹窗、也不用浮层卡片**：上传和在线匹配都可能花上十几秒，把进度浮在屏幕上挡着自己是没必要的。进度条、状态标签和解析动效都长在各自那一行上，所以「哪一首正在解析歌词」一眼就能看到——那一行的图标就是一排跳动的电平柱。上传和在线匹配拿不到真实字节数，这两步用一条流动的条纹表示「还在动」，而不是假装知道百分比。跑完自动收起，出错的那行留着等你看；切到别的页面时，顶部导航的「音乐」上会挂一个处理中的计数。曲目行上另有「⟳ 解析歌词中 / ✓ 有歌词 / 暂无歌词」的状态标签。

按可靠性从高到低一共四层，前一层拿不到才往下走：

| 顺序 | 来源 | 说明 |
| --- | --- | --- |
| 1 | 数据库里已存的 `media_assets.lyrics` | 手动确认过的那一份，永远优先 |
| 2 | 音频文件内嵌标签 | ID3v2 的 `USLT` / `SYLT` / `TXXX`，自己写的解析器，不引依赖 |
| 3 | [LRCLIB](https://lrclib.net) | 免费开源、无需 key、支持浏览器跨域；按「曲名 + 歌手 + 时长」精确匹配，失败再模糊搜索 |
| 4 | 中文源（网易云） | 中文覆盖最好，但它的接口不带 CORS 头也不许设 Referer，必须经 `supabase/functions/lyrics` 中转 |

四层都没命中不是报错，而是把控制权交回给你：右栏变成「粘贴 / 上传 LRC」。手动保存的那一份会覆盖自动匹配的结果，`lyrics_source` 记着它是从哪来的。

存的是 **LRC 原文**而不是解析结果：这样自动匹配到的那份可以被你直接改时间轴再存回去，前后端也不用维护两套格式。时间轴、当前句定位、乱序排序、`[offset:]`、`[mm:ss:xx]` 这种不规范写法都有 `npm run verify:lyrics` 覆盖。

老曲目（这次改动之前上传的）在第一次播放时补解析一次；也可以点曲库上方的「补全歌词」把缺的批量匹配一遍。

### 音频卡顿排查：一条用两次踩坑换来的铁律

> **播放期间，绝不在后台下载任何东西。**

这条规则是两次真实故障换来的，两次都是同一个错误：**在播放旁边又开了一路下载**。

| # | 我加的东西 | 症状 | 实测证据 |
| --- | --- | --- | --- |
| 1 | `probeDuration`：为了给 LRCLIB 补一个 `duration` 字段，另建一个 `<audio>` 把**同一个文件**再下载一遍 | 「播一下卡一下」 | `waiting` 连续触发而 `stalled` 为 0——数据在到，只是被分走了一半 |
| 2 | 曲目预取：页面一打开就后台整段下载前两首歌（每首约 3.5 MB） | 直接**播放不了** | 同一个地址 `fetch` 能拿到 44 KB/s，而媒体元素的请求被饿到 **24 秒不出一个字节** |

排查手段是给页面装一条探针时间线（记录媒体元素的 `loadstart / waiting / stalled / error` 和每秒的 `readyState / networkState / currentTime`），再由页面把日志发回本机的一个小 HTTP 服务。修复后的时间线：

```
CLICK t=0
+3.5s   rs=4  t=0.84      ← 3.5 秒开始出声
+5.6s   rs=4  t=2.85
+7.6s   rs=4  t=4.85      ← 每 2 秒正好 +2.00 秒
+33.5s  rs=4  t=30.84     ← 全程 ns=1（浏览器都不需要再下载）
```

`readyState` 恒为 4（缓冲充足）、`networkState` 恒为 1（网络空闲）——这才是没有卡顿的样子。

### 现在是怎么播的

- **本机试听 / 刚上传的曲目**：直接播本地文件，完全不碰网络。
- **曲库里的曲目**：**只在没有播放的时候**在后台整段取回并缓存成 blob（`fetch` 的顺序读取比媒体元素那套「302 + 分段 Range」高效得多，实测同一个地址 fetch 拿得到的数据媒体元素拿不到）。缓存好的曲目之后一直播本地源。
- **一开播就立刻掐断在途的后台下载**，而且是**在用户点下去的那一瞬间**同步掐断——不能等 `playing` 变 true，那要等 `play()` 成功，而在那之前下载还在占带宽。
- 缓存过的曲目如果播不出来，`@error` 会自动切回在线地址重试一次，不会变成「完全没声」。

### 让起播不再等待：提前预缓冲 + 预连接

起播慢有很大一部分不是带宽问题，而是**一条很长的握手链**：DNS → TLS → 签名地址 → 302 跳转 → 真实对象 → Range 分段。音频要等这条链走完、再凑够头几百 KB 才出声。两条零风险的改善：

- **预连接**（`services/api.js`）：模块加载时就往 `<head>` 里注入 `preconnect` 与 `dns-prefetch`，把 DNS 和 TLS 握手提前做掉。
- **提前预缓冲**（`preloadFirstTrack`）：打开音乐页、**且没有在播放**时，就把队列第一首的地址交给 `<audio>` 并设 `preload="auto"`，让浏览器先缓冲。等你点播放时数据已经在缓冲区里，起播几乎是瞬时的。

这**不违反**上面那条「播放期间不后台下载」的铁律：这里下载的就是你点播放后要下的同一个文件、走的还是媒体元素自己那条流，只是**提前开始**——没有第二路下载，也没有等整段。换歌时旧请求会被新的 `src` 自动中断。

配套的关键一点：`playMusicItem` 在**源地址已经相同**时绝不再调用 `load()`——那会把已经缓冲好的数据整段丢掉、从头再来一遍，预缓冲就白做了。

### 省电模式

标题栏的 `完整动效 / 省电模式` 会完全跳过 Web Audio 的建图、关掉粒子场与两块频谱画布，用来排除渲染与音频图这一侧。（音频图一旦建立就和当时那个 `<audio>` 元素绑死了，所以切换时模板里 `<audio>` 的 `key` 会跟着变，Vue 重新创建一个干净的元素，播放会中断，这是刻意的。）

### 封面与头像的保存方式

文章的 `coverUrl` 和账号的 `avatarUrl` 里保存的是**两种值之一**：一个绝对图片地址，或者本项目的引用写法 `media:<媒体 id>`。之所以不直接存签名链接，是因为媒体的签名读取链接只有 1 小时有效期，存下来会过期；存引用则可以随时重新解析。前端在渲染时把它解析回当前有效的链接。

### 关于签名链接有效期

媒体地址是 **1 小时**有效的签名链接（`LINK_TTL`，定义在 `frontend/src/services/api.js`）。
页面长时间开着不刷新时，图片会在链接过期后失效，刷新即可恢复。
文章封面和头像存的是绝对地址或 `media:<媒体 id>` 引用——存引用正是因为签名链接会过期。

### 什么东西存在服务端，什么东西只在本机

| 内容 | 存哪 |
| --- | --- |
| 账号 | Supabase Auth |
| 文章、日记、媒体元数据、绩效工作区 | Postgres（RLS 控制可见范围） |
| 图片、音频文件本体 | Supabase Storage |
| **留言板、友链** | **只在当前浏览器的 localStorage**（还没有后端表；界面提示写的是「已添加到预览」） |
| 博客首页开关、日记默认可见范围、可视化模式、省电模式、学习进度 | 本机偏好，不落库 |

**不要把浏览器里的东西当作服务器备份。**
